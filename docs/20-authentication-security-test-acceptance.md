# Authentication security test acceptance

## Purpose and layers

The complete authentication and account-security acceptance gate is three layers, all required for authentication/account-security changes and all run by the `security` job in `.github/workflows/auth-security-verification.yml` on every pull request targeting `main`:

1. **`pnpm test:ci`** (unit/pure-logic layer) — includes, among the repository's full unit suite, exact-boundary JWT/session tests (`tests/session-token-boundaries.test.ts`: idle/absolute timeout at the exact millisecond, malformed/tampered/wrong-algorithm/expired-claim JWT rejection, production-vs-development cookie attributes via injected environment) and exhaustive Turnstile fail-closed tests (`tests/turnstile-contract.test.ts`: network failure, non-OK provider status, malformed provider body, missing/undersized secret or `BASE_URL` in every `NODE_ENV`, no bypass in any environment).
2. **`pnpm test:integration-db`** (isolated-PostgreSQL layer) — the existing integration suites (OTP digesting, purpose binding, exhaustion and expiry; password policy and reset invalidation; persisted-session replay and revocation; ownership checks; role transitions; MFA recovery, replacement and step-up; rate limiting; enumeration timing; secret-free audit evidence) plus, added for this gate's completeness: real-Postgres session-registry adversarial tests (missing/revoked/wrong-user rows, revocation-reason irrelevance, concurrent revoke-vs-touch races, idempotent re-registration), Google OAuth transaction adversarial tests (state replay, purpose-mismatch at both the application and database-constraint layers, expiry, origin/redirect-URI mismatch, provider-error surfacing, retention purge) without ever contacting the real Google provider, Google account-linking tests (no-auto-link enforcement including case/whitespace email variants, ineligible-account rejection on a subsequent login), email-OTP cross-purpose rejection, and rate-limit normalized-email-bypass resistance.
3. **`pnpm test:security-e2e`** (Playwright/Chromium HTTP-boundary layer) — the existing specifications (anonymous denial, direct-request role and account-state enforcement, onboarding and expired-account routing, pending-cookie/session separation, real registry-backed session recognition, development cookie attributes, response security headers) plus, added for this gate's completeness: a dedicated session-replay specification that forges tokens *outside* the shared fixture (which always creates a matching registry row) to prove a missing row, a `sessionVersion` mismatch, and a directly-revoked row are all rejected end-to-end with a positive control; and a dedicated CSRF specification that proves the real running application rejects a forged cross-origin `Origin` header on a Server Action request before the action is looked up, distinguishes that from the same request sent same-origin, and confirms an authenticated session survives the rejected forgery attempt unaffected.

Deterministic synthetic fixtures include two active members, onboarding, expired, suspended, Administrator, and Super Administrator identities. They are created directly in the isolated database; no public test endpoint, authentication bypass, email delivery, Google request, Turnstile request, or production secret is used anywhere in this gate.

Playwright intentionally does not reproduce database concurrency, high-count abuse limits, cryptographic OTP/TOTP/recovery invariants, or provider callback internals when integration tests prove those properties more deterministically. Billing and payment security is excluded except for authorization boundaries.

[Authentication & account-security control inventory](21-authentication-security-control-inventory.md) is the control-by-control map behind this gate: for every implemented authentication/authorization/session/MFA/OAuth/CSRF/rate-limit/account-state/cookie/header control it records the exact code and database location, the exact test file(s), whether each test is behavioral (executes the code) or source-inspection (asserts the code's shape by pattern), and whether the control is proven end-to-end by this repository's own suite, proven only by source inspection, or not yet covered at all. Document 21 §9 is the authoritative, current list of behaviors that remain source-inspection-only or genuinely untested after the expansion described above — the list is now short: real Google JWKS/token-exchange trust establishment (inherently external-provider-dependent, not automatable locally), the OAuth login-CSRF binding cookie's specific cross-site-forgery scenario, a full production-mode server boot's browser-enforced `__Host-` cookie behavior (the cookie's *values* are now proven directly), and fail-closed behavior on a corrupted MFA factor record. Document 21 §7.1–§7.3a and §12 record the two behaviors that remain genuinely not implemented at all as of this document's current revision: no application-level CSRF token beyond the Next.js Server Action origin-mismatch check (that check itself is now behaviorally proven), and the legacy token/link account-recovery path's rate limiting has not been migrated to the dual-bucket design used elsewhere — these are gaps, not test-coverage omissions, and are not represented as passing anywhere in this repository's test output. (Application-level HSTS, previously listed here as a gap, is implemented and tested as of this revision.)

## Running locally

1. Supply a PostgreSQL URL whose database name unmistakably contains `test` in `TEST_DATABASE_URL`; the guard rejects missing, ambiguous, production-equivalent, or non-PostgreSQL targets.
2. Install Chromium once with `pnpm exec playwright install chromium`.
3. Run `pnpm test` (or `pnpm test:ci` for CI-style dot output) for the unit layer, then `pnpm test:security` for the integration-DB and Playwright layers together. Playwright starts and stops the application on port 3100, recreates only the `idoc` schema in the guarded database, and uses synthetic secrets.

Never target a shared developer or production database. Fixture reset is destructive within the test database's `idoc` schema. Generated storage states and traces are ignored by Git.

## Continuous integration and evidence

The dedicated `auth-security-verification.yml` workflow provisions PostgreSQL 16, runs `pnpm typecheck` and `pnpm test:ci` (the unit layer, including the exact-boundary session and Turnstile tests described above), installs Chromium, then runs `pnpm test:security` (the integration-DB and Playwright layers), and fails on any failed assertion at any layer — a green `security` check on a pull request is a complete auth/security gate on its own, not dependent on any other workflow also being green. Compact output is retained normally; reports, traces, screenshots, and video are uploaded for seven days only after failure.

## Independent assurance still required

Automation is not penetration-test certification. Independent review remains required for deployed CDN/Vercel configuration, real Google/Turnstile/Mailchimp provider and DNS behavior (this repository's tests exercise all repository-controlled OAuth transaction/purpose/replay/linking logic without contacting the real Google provider, per document 21's testing principles, but the live JWKS/token-exchange trust handshake itself remains external-provider-dependent), secret rotation and incident response, social engineering and credential stuffing at realistic scale, browsers outside Chromium, dependency/infrastructure compromise, and novel chained business-logic attacks. Payment/subscription abuse remains a separate future suite.

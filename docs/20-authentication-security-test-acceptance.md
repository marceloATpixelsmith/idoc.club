# Authentication security test acceptance

## Purpose and layers

The complete authentication and account-security acceptance gate is three test layers plus a dependency/supply-chain scan, all required for authentication/account-security changes and all run by the `security` job in `.github/workflows/auth-security-verification.yml` on every pull request targeting `main`:

1. **`pnpm test:ci`** (unit/pure-logic layer) — includes, among the repository's full unit suite, exact-boundary JWT/session tests (`tests/session-token-boundaries.test.ts`: idle/absolute timeout at the exact millisecond, malformed/tampered/wrong-algorithm/expired-claim JWT rejection, production-vs-development cookie attributes via injected environment), exhaustive Turnstile fail-closed tests (`tests/turnstile-contract.test.ts`: network failure, non-OK provider status, malformed provider body, missing/undersized secret or `BASE_URL` in every `NODE_ENV`, no bypass in any environment), and — added for the SaaS-baseline gap-remediation pass — password-breach-check tests (`tests/password-breach-check.test.ts`: real suffix match/no-match against the HaveIBeenPwned range API, only the 5-character prefix ever sent, fail-open on non-OK status/network failure/request-timeout) and source-inspection wiring tests (`tests/password-security-hardening.test.ts`: every password-creation/change call site checked for a breach before writing, the login password-guessing throttle checked before any credential comparison, the legacy account-recovery path's dual-bucket migration, the new-sign-in alert's role gating, the `account_state` database constraint).
2. **`pnpm test:integration-db`** (isolated-PostgreSQL layer) — the existing integration suites (OTP digesting, purpose binding, exhaustion and expiry; password policy and reset invalidation; persisted-session replay and revocation; ownership checks; role transitions; MFA recovery, replacement and step-up; rate limiting; enumeration timing; secret-free audit evidence) plus real-Postgres session-registry adversarial tests (missing/revoked/wrong-user rows, revocation-reason irrelevance, concurrent revoke-vs-touch races, idempotent re-registration), Google OAuth transaction adversarial tests (state replay, purpose-mismatch at both the application and database-constraint layers, expiry, origin/redirect-URI mismatch, provider-error surfacing, retention purge) without ever contacting the real Google provider, Google account-linking tests (no-auto-link enforcement including case/whitespace email variants, ineligible-account rejection on a subsequent login), email-OTP cross-purpose rejection, rate-limit normalized-email-bypass resistance, a behavioral proof that rotating the origin alone can no longer bypass the legacy account-recovery path's per-email allowance, a behavioral proof that the new `login_password` throttle purpose is independently bucketed by email and by origin, a behavioral proof (real Postgres, real HTTP calls to a stubbed provider — never the live HaveIBeenPwned/Mailchimp endpoints) that a breached password is rejected without consuming the caller's recovery token and correctly alerts the configured operations recipient while excluding the password itself from that alert, and — added for the WebAuthn/passkey pull request — 13 real-Postgres tests covering credential registration's active-TOTP-fallback precondition, ownership-scoped credential lookup and revocation, sign-count replay rejection (including the zero-counter spec allowance), purpose-bound single-use ceremony challenges, and two concurrency races (duplicate credential-ID registration; the shared MFA store's generic challenge-completion path).
3. **`pnpm test:security-e2e`** (Playwright/Chromium HTTP-boundary layer) — the existing specifications (anonymous denial, direct-request role and account-state enforcement, onboarding and expired-account routing, pending-cookie/session separation, real registry-backed session recognition, development cookie attributes, response security headers) plus a dedicated session-replay specification that forges tokens *outside* the shared fixture (which always creates a matching registry row) to prove a missing row, a `sessionVersion` mismatch, and a directly-revoked row are all rejected end-to-end with a positive control; a dedicated CSRF specification that proves the real running application rejects a forged cross-origin `Origin` header on a Server Action request before the action is looked up, distinguishes that from the same request sent same-origin, and confirms an authenticated session survives the rejected forgery attempt unaffected; a specification proving the RFC 9116 vulnerability-disclosure policy is served at `/.well-known/security.txt` with well-formed `Contact`/`Expires`/`Canonical` fields; and — added for the WebAuthn/passkey pull request — a specification driving a genuine CDP virtual authenticator through a real registration and removal ceremony against the live dev server (not a mock), including the fresh-step-up TOTP round each sensitive action requires. That specification alone addresses the app at `localhost` rather than the suite's usual `127.0.0.1` (a bare IP is not a valid WebAuthn relying-party ID); every other specification is unaffected.
4. **Dependency/supply-chain scanning** (not a test suite, but part of the same required `security` check) — `pnpm audit --audit-level=critical` fails the build on any critical advisory; `pnpm audit --audit-level=high` reports high/moderate advisories without yet failing the build, since the dependency tree carries several pre-existing high-severity transitive advisories that predate this gate (see document 21 §12). Dependabot (`.github/dependabot.yml`) opens weekly pull requests toward closing these.

Deterministic synthetic fixtures include two active members, onboarding, expired, suspended, Administrator, and Super Administrator identities. They are created directly in the isolated database; no public test endpoint, authentication bypass, email delivery, Google request, Turnstile request, or production secret is used anywhere in this gate.

Playwright intentionally does not reproduce database concurrency, high-count abuse limits, cryptographic OTP/TOTP/recovery invariants, or provider callback internals when integration tests prove those properties more deterministically. Billing and payment security is excluded except for authorization boundaries.

[Authentication & account-security control inventory](21-authentication-security-control-inventory.md) is the control-by-control map behind this gate: for every implemented authentication/authorization/session/MFA/OAuth/CSRF/rate-limit/account-state/cookie/header/supply-chain control it records the exact code and database location, the exact test file(s), whether each test is behavioral (executes the code) or source-inspection (asserts the code's shape by pattern), and whether the control is proven end-to-end by this repository's own suite, proven only by source inspection, or not yet covered at all. Document 21 §9 is the authoritative, current list of behaviors that remain source-inspection-only or genuinely untested — real Google JWKS/token-exchange trust establishment (inherently external-provider-dependent, not automatable locally), the OAuth login-CSRF binding cookie's specific cross-site-forgery scenario, a full production-mode server boot's browser-enforced `__Host-` cookie behavior (the cookie's *values* are proven directly), fail-closed behavior on a corrupted MFA factor record, and — added by the SaaS-baseline gap-remediation pass — the four Server-Action call sites for the new password-breach check and login throttle, which are proven by source inspection plus a behaviorally-proven underlying primitive rather than a full Playwright round-trip (matching how no other password-creation Server Action in this repository is directly e2e-tested either). Document 21 §7.1 and §12 record what remains genuinely not implemented at all: no application-level CSRF token beyond the Next.js Server Action origin-mismatch check (that check itself is behaviorally proven), and no request-scoped correlation ID / APM integration — these are gaps, not test-coverage omissions, and are not represented as passing anywhere in this repository's test output. (Application-level HSTS, the legacy account-recovery path's dual-bucket rate limiting, and the WebAuthn/passkey option for privileged roles, all previously listed here as gaps, are implemented and tested as of this revision — the WebAuthn ceremony verification library itself is trusted rather than independently re-verified, matching this document's existing treatment of `jose`/`bcryptjs`; see document 21 §12.)

## Running locally

1. Supply a PostgreSQL URL whose database name unmistakably contains `test` in `TEST_DATABASE_URL`; the guard rejects missing, ambiguous, production-equivalent, or non-PostgreSQL targets.
2. Install Chromium once with `pnpm exec playwright install chromium`.
3. Run `pnpm test` (or `pnpm test:ci` for CI-style dot output) for the unit layer, then `pnpm test:security` for the integration-DB and Playwright layers together. Playwright starts and stops the application on port 3100, recreates only the `idoc` schema in the guarded database, and uses synthetic secrets.

Never target a shared developer or production database. Fixture reset is destructive within the test database's `idoc` schema. Generated storage states and traces are ignored by Git.

## Continuous integration and evidence

The dedicated `auth-security-verification.yml` workflow provisions PostgreSQL 16, runs `pnpm audit --audit-level=critical` (build-blocking) and `pnpm audit --audit-level=high` (report-only — see document 21 §12 for why), `pnpm typecheck` and `pnpm test:ci` (the unit layer, including the exact-boundary session, Turnstile, and password-breach-check tests described above), installs Chromium, then runs `pnpm test:security` (the integration-DB and Playwright layers), and fails on any failed assertion at any layer — a green `security` check on a pull request is a complete auth/security gate on its own, not dependent on any other workflow also being green. Compact output is retained normally; reports, traces, screenshots, and video are uploaded for seven days only after failure.

## Independent assurance still required

Automation is not penetration-test certification. Independent review remains required for deployed CDN/Vercel configuration, real Google/Turnstile/Mailchimp provider and DNS behavior (this repository's tests exercise all repository-controlled OAuth transaction/purpose/replay/linking logic without contacting the real Google provider, per document 21's testing principles, but the live JWKS/token-exchange trust handshake itself remains external-provider-dependent), secret rotation and incident response, social engineering and credential stuffing at realistic scale, browsers outside Chromium, and novel chained business-logic attacks. Dependency/supply-chain risk is now partially automated (Dependabot plus the two-tier `pnpm audit` gate described above) but not fully closed: several pre-existing high-severity transitive advisories remain unresolved (document 21 §12), so this is meaningfully better than no scanning, not a clean bill of health. Payment/subscription abuse remains a separate future suite.

# Release 1 behavioral verification matrix

## Status and evidence rules

This matrix records the verification available on this branch. **Release 1 remains open.** A row is `Verified` only when the named test exercises the behavior against isolated PostgreSQL and the command passed. Unit tests and source inspection are listed only as supplemental evidence and never turn a database requirement green. `Not yet verified` is an acceptance blocker, not an assertion that the implementation is defective.

The implementation boundaries use these abbreviations: `migration` = `lib/db/migrations` and Drizzle metadata; `DB guard` = `lib/db/test-database-url.ts` and `scripts/run-integration-db.ts`; `membership` = `lib/membership`; `delivery` = `lib/notifications`; `auth` = `lib/auth` plus login actions; `configuration` = `lib/runtime/configuration.ts`.

## Reconciliation of merged PR #22–#25 evidence

This section corrects claims made in earlier revisions of this document. Those revisions promoted several rows to `Verified` on the basis that a PR's "Run Release 1 gate" check had "reported green" or "passed" for its final revision. Inspecting the actual GitHub Actions results for PR #22 through #25 (not merge status, not commit messages) shows this was false for every one of the four PRs:

| PR | Head commit | Actual "Run Release 1 gate" result |
|---|---|---|
| #22 | `5913c44` | **Failed** — completed after ~55 minutes with 20 of 33 tests failing |
| #23 | `28bc105` | **Failed** — completed after ~58 minutes with 23 of 35 tests failing |
| #24 | `3357252` | **Never completed** — still "in_progress" hours after the PR merged |
| #25 | `6fa5c0d` | **Never completed** — still "in_progress" hours after the PR merged |

All four PRs were merged without a passing (or even completed) gate on their head commit. This corrective batch found and fixed the actual root causes:

1. **A `postgres.js` `Date`-serialization crash.** `tests/postgres-harness.ts`'s `createUser()` passed a raw `Date` object into a tagged-template query parameter that is sometimes `null` (unverified accounts) and sometimes a `Date` (every other state) for the same query text. This triggered a `TypeError` deep inside `postgres.js`'s `Bind()` path (`"The string argument must be of type string or an instance of Buffer or ArrayBuffer. Received an instance of Date"`), cascading into most of the ~20 failures seen in the PR #22/#23 runs. Two production call sites had the identical pattern: `lib/membership/account-recovery.ts`'s `takeAllowance()` (a rate-limit upsert) and `lib/notifications/account-delivery.ts`'s `claimAccountDelivery()`/eligibility recheck (both raw `sql` templates executed via Drizzle's `db.execute()`). All three now pass ISO date strings instead of raw `Date` objects, with explicit `::timestamptz` casts where a `CASE` expression's `NULL` branch would otherwise force an ambiguous "unknown" type.
2. **A real, previously-undiscovered production defect.** `claimAccountDelivery()`'s raw SQL used `RETURNING outbox.*`, which returns PostgreSQL's native snake_case column names (`encrypted_payload`, `token_id`, `user_id`, `message_id`, `attempt_count`, …), but every caller read camelCase properties (`record.encryptedPayload`, `record.tokenId`, …) — all `undefined` at runtime. This meant **every real account-delivery send (password reset, migration activation) had always silently failed**, retried, and eventually dead-lettered; nothing ever actually reached the Mailchimp Transactional boundary in production use, though the failure was invisible because the worker's `catch` block does not log the underlying exception (by design, to keep operational evidence free of raw exceptions). Fixed by aliasing every returned column to its camelCase name in the `RETURNING` clause.
3. **A genuine catalog/schema.ts drift**, only reachable once (1) and (2) stopped masking it: migration `0006` created two `account_delivery_outbox` unique constraints and one `account_request_limits` uniqueness rule without matching `schema.ts`'s naming/shape (PostgreSQL auto-named two constraints `..._key` instead of `..._unique`; the third was created as a table constraint where `schema.ts` declares a plain unique index). A new forward-only migration `0010_workable_dagger.sql` (following the same pattern already established by migration `0009`) reconciles the catalog to match the declared schema without rewriting released migration history or changing enforced behavior. `tests/migration-immutability.test.ts`'s existing `the current schema exports exactly generate the authoritative migration snapshot` test independently confirms a fresh `drizzle-kit generate` from `schema.ts` now produces content identical to the new `meta/0010_snapshot.json`.
4. **Several genuine test-only defects** that had never been exercised because the above always crashed first: a stale pre-`0009` foreign-key constraint name in `tests/database-integration.integration.ts`; an exact-column-*order* assertion that can never hold once any column is added by a later `ALTER TABLE` (physical order always reflects migration history, not `schema.ts` declaration order — fixed to compare the column set instead); a missing `timestamp` → `timestamp without time zone` case in that test's type-normalization helper; a transposed word order in a trigger-definition regex (`/BEFORE UPDATE OR DELETE/` vs PostgreSQL's actual `BEFORE DELETE OR UPDATE`); `tests/database-target-guard.integration.ts` comparing a `postgres.js` `Result` (which carries extra own properties beyond its array elements) against a bare array literal via `assert.deepEqual`, which always fails regardless of content; a fixture URL in that same file that was listed as an expected-rejection case but is not actually rejected by `validateTestDatabaseUrl` (the function's own already-passing unit test proves remote non-localhost hosts are accepted by design — this was a mistake in the new integration test's fixture, not a validation gap, and was **not** weakened); `tests/account-token-lifecycles.integration.ts` passing a raw `Date` into the same harness client; and `scripts/run-integration-db.ts`'s top-level `await`, which fails to transform when the module is *imported* (as `database-target-guard.integration.ts` does, to test `runIntegrationDatabase` directly) rather than executed directly — rewritten as a fire-and-forget `.catch()` with no change to the real entry point's behavior.

None of these were weakenings of authorization, validation, rate limiting, token security, audit immutability, or transaction atomicity. Every fix either corrected a test-only assertion to check what it actually claims to check, or corrected a real production/tooling defect and added no new exception to any enforced rule.

Every named test below that this reconciliation batch touched has been re-run against real disposable PostgreSQL (a locally provisioned PostgreSQL 16 instance, not Render, not `POSTGRES_URL`) and passed. That corrective batch became PR #27, and its "Run Release 1 gate" check on the final head commit (`a572301`) **actually completed and passed** against a fresh disposable PostgreSQL 16 GitHub Actions service container (started 2026-08-13T20:30:23Z, completed 2026-08-14T01:29:40Z) — the first time in this document's history that claim is genuinely true, confirmed by inspecting the workflow run directly rather than merge status. PR #27 merged as commit `9a31171` on `main`. Every row below citing this evidence now reflects both the local run and this confirmed CI result.

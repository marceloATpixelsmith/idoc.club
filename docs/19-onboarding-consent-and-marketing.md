# Onboarding consent and marketing

## Implemented behavior

New members must explicitly accept the Terms of Service and Privacy Policy when they submit onboarding. "Keep me updated" is optional and checked by default. Server-side validation rejects missing required acceptance regardless of browser validation.

The profile, roles, consent evidence, audit evidence, and account-state transition commit in one PostgreSQL transaction. `idoc.onboarding_consents` is a one-to-one child of the newly created profile and records the actual submission time for both required acceptances plus the submitted marketing choice. Migration `0019_onboarding_consents` does not backfill the table: imported or otherwise existing profiles without real submission evidence remain without a consent row.

After an opted-in onboarding transaction commits, the server makes a best-effort Mailchimp Marketing add-or-update request. It first reads the member's Mailchimp status and then sends `status` and `status_if_new` as `subscribed` for a new or archived member (a member who is already subscribed is left alone). A member who previously **unsubscribed themselves** cannot be resubscribed that way (Mailchimp answers 400), so they are sent Mailchimp's confirmation email instead; see "Marketing preference stays in sync with Mailchimp" below. The request has a five-second timeout. Missing configuration, provider rejection, network failure, or timeout cannot roll back onboarding and has no Stripe, payment, billing, entitlement, or subscription effect.

Self-service membership cancellation (docs/02 §5.1) makes the mirror-image best-effort request, setting only `status` to `unsubscribed` (never `status_if_new`, so a member with no existing Mailchimp record is not given one just to mark it unsubscribed). The same isolation applies in both directions: this call can never block, fail, or roll back the membership-level cancellation it accompanies.

## Marketing preference stays in sync with Mailchimp

`onboarding_consents.keep_updated_opt_in` is the member's "Keep me updated by email" setting. It is true only while Mailchimp holds the member as **subscribed**. Migration `0079_marketing_preference_sync` adds `keep_updated_changed_at`, `keep_updated_source` (`member`, `admin`, `mailchimp_webhook`, `mailchimp_reconciliation`) and `keep_updated_pending_at`. Every change after onboarding writes an audit entry (`member.marketing_preference.changed`). The flag only ever describes the Mailchimp marketing audience; **it is never read by, and can never block, any system email** (account, verification, security, billing, renewal, seminar and operational mail all go through Brevo Transactional without consulting it). `tests/mailchimp-marketing-webhook.test.ts` fails if any code outside the marketing module reads the flag.

**Mailchimp to the app.** Two mechanisms update the flag, and neither sends a message or touches billing, entitlement or account state:

- *Webhook:* `POST /api/mailchimp/webhook?key=<MAILCHIMP_WEBHOOK_KEY>` (GET answers 200 for Mailchimp's URL check). Mailchimp does not sign deliveries, so the shared key in the query string is the authentication (timing-safe comparison; 503 when unset, 400 when wrong). Mailchimp posts form-encoded fields (`type`, `data[email]`, `data[list_id]`). Events for another audience are ignored. `unsubscribe` and `cleaned` clear the flag; `subscribe` sets it only for a member whose opt-in was waiting on confirmation (below). Other event types and unknown addresses are accepted and ignored. Processing failures return 500 so Mailchimp retries.
- *Daily reconciliation* (`/api/cron/marketing-preference-sync`, QStash job `marketing-preference-sync`, 08:30 UTC): reads every `unsubscribed` and `cleaned` address from the Mailchimp audience (paged) and clears the flag for matching members, then completes any opt-in whose confirmation email was clicked. It is also the one-time backfill for members who unsubscribed before the webhook existed: run it once per environment after configuring Mailchimp (fire the route with the `CRON_SECRET` bearer header). It never re-subscribes anyone, only reads from Mailchimp, and fails the run (rather than reporting "nobody unsubscribed") when Mailchimp cannot be read.

**App to Mailchimp.** The My Profile page and the administrator member drawer show the setting as a toggle.

- *Opting out* (member or administrator) is saved locally first and then sent to Mailchimp as `unsubscribed`; if Mailchimp cannot be reached the choice is still honored locally and the member is told the provider could not be reached. An administrator can only switch the setting off; opting in is the member's own consent.
- *Opting in* needs Mailchimp's agreement. A member Mailchimp has never seen, or one it holds as subscribed, is subscribed immediately. Mailchimp refuses `subscribed` for anyone who **unsubscribed themselves** (HTTP 400, "Member In Compliance State"), so those members are sent Mailchimp's confirmation email (status `pending`); the flag stays false with `keep_updated_pending_at` set, and the page says to check their inbox. It becomes true only when the webhook or reconciliation reports `subscribed`. Turning the toggle off while pending cancels it. A cleaned (permanently undeliverable) address cannot be re-subscribed and the member is told so. When the launch hold is on, or Mailchimp is unconfigured or failing, opting in changes nothing and the member sees a "try again later" notice. None of these outcomes fails the profile save.
- *Onboarding* uses the same rules and keeps the flag truthful: a checked box subscribes new members directly, while an imported member who had unsubscribed in Mailchimp is sent the confirmation email and starts with the flag false and pending. If Mailchimp is unreachable or unconfigured, or the launch hold is on, the flag is also corrected to false (the original onboarding choice is kept in the audit entry), so the member sees the toggle off and can switch it on later; nothing is retried automatically.

Verified against the live Mailchimp API (October 2026): an API/admin unsubscribe can be reversed with `PUT status=subscribed`; a self-unsubscribe cannot (400) but `PUT status=pending` sends the confirmation email and the member becomes subscribed when they click it.

## Runtime configuration

The server-only integration uses `MAILCHIMP_MARKETING_API_KEY`, `MAILCHIMP_MARKETING_SERVER_PREFIX`, and `MAILCHIMP_MARKETING_AUDIENCE_ID`; the inbound webhook additionally needs `MAILCHIMP_WEBHOOK_KEY` (random, 32 or more characters, distinct per environment). If any API value is absent, onboarding still completes and no provider call is attempted.

To enable the webhook, in Mailchimp open Audience > Settings > Webhooks > Create new webhook with the URL `https://<host>/api/mailchimp/webhook?key=<MAILCHIMP_WEBHOOK_KEY>`, tick **Subscribes**, **Unsubscribes** and **Cleaned**, tick all three sources (by a subscriber, by an admin, via API), then click Save. Do this per environment, each with its own key. These values must never be exposed to browser code or persisted as consent evidence.

Onboarding presentation: both onboarding steps ("What kind of official are you?" and "Complete your profile") render without the auth-page horse image. The first step is a single-select radio list showing only each option's name beside its established member-type icon (Bell for Judge, Horseshoe for Steward, both for Judge + Steward, Stethoscope for Veterinarian). The Terms of Service (`/terms`) and Privacy Policy (`/privacy`) pages render inside the standard marketing layout, with the site header and footer, as ordinary content pages.

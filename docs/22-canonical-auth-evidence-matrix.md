# 22. Canonical Auth Contract Evidence Matrix

## Purpose and scope

This document is the current, from-scratch evidence matrix for every requirement in the canonical
`pixelsmith-auth-reference` machine contract (`src/contract/requirements.ts`), evaluated against the
actual idoc.club codebase as of this revision. It supersedes any prior evidence-matrix claims in
`docs/21-authentication-security-control-inventory.md` as the authoritative status source; docs/21
retains its own descriptive sections (cookie attribute table, CSRF/rate/header/Turnstile/config/log/DB/
supply-chain notes, and its changelog of individual pull requests) and is not being deleted, but its
per-requirement status claims should be read as historical narrative, not current status — this
document is current status.

**Canonical versions confirmed at the time of this audit** (independently reproduced from the canonical machine artifacts on `pixelsmith-auth-reference` `main`): contractVersion 2.0.0, machine schemaVersion 14.0.0, validatorVersion 11.0.0,
mapping schemaVersion 1.0.0, portable-config schemaVersion 2.0.0.

## Methodology

Five independent evidence-gathering passes were run against the current idoc.club codebase, one per
canonical contract stage (Foundational + Stage 2 session/cookie/CSRF/rate/bot/error/redirect/transport/
API/framework/storage; Stage 3 signup/email/OTP/password; Stage 4 MFA/TOTP/recovery/remembered-device;
Stage 5 OAuth/invite/tenant/authorization; Stage 6 log/audit/operations/crypto-lifecycle/privacy/
dependency-failure). Each pass traced the actual trusted-server call chain for every requirement in
scope — reading the implementation, its persistence layer, and its test evidence directly — rather than
inferring behavior from file or function names. IDOC's own `docs/21` inventory uses an independent local
ID-numbering scheme that only coincidentally matches canonical IDs at low numbers; this matrix is keyed
to the canonical IDs directly, cross-referencing docs/21's local IDs only where explicitly noted.

### Assessment legend

- **verified** — real behavioral evidence exists (a test that executes the actual production code path
  against real infrastructure — Postgres, a real browser, a signed JWT — and observes the result), not
  merely source inspection.
- **implemented-but-unverified** — the implementation is present and reads correctly on direct code
  inspection, but no behavioral test exercises the actual production code path; existing test coverage
  (if any) is source-inspection-only (regex assertions against file text) or exercises a different,
  parallel code path than the one production actually calls.
- **partial** — a real, specific gap exists in an otherwise-implemented control. The gap is named
  explicitly in the Notes column, not glossed over.
- **missing** — no implementation exists for a requirement that applies to IDOC's product model.
- **not-applicable** — the requirement does not apply given IDOC's confirmed product model (single-
  tenant, single-application; TOTP is compulsory-by-role rather than optional-per-user; a given feature
  is implemented in code but has zero production callers and is therefore inert), with rationale stated.

### IDOC product model, as confirmed by this audit

IDOC is a **single-tenant, single-application platform**: one Vercel deployment, one Postgres schema,
no organization/tenant entity anywhere in the schema used as an authorization boundary (`memberships`
records club-entitlement status, not organizational membership). The `invitations` table and
`ActivityType.INVITE_TEAM_MEMBER`/`'invite-privileged-user'` are genuinely unreferenced Vercel
SaaS-starter-template leftovers (`grep`-confirmed zero call sites outside schema/type definitions). There
is no invitation flow; Administrator/Super Admin accounts are provisioned by an existing Super Admin
directly calling `grantApplicationRole` (`lib/membership/role-grants.ts`), a documented deliberate policy
(docs/05 §4, docs/07 §11), not an omitted feature. This makes AUTH-INVITE-001/002/003 correctly
not-applicable. **The `teams`/`team_members` tables were a separate case, now fixed**: `app/layout.tsx`
called `getTeamForUser()` on every request as a live (if unpopulated) SWR-fallback query — a Codex review
on the PR that introduced this document correctly caught an earlier draft's claim that this was dead
code, and AUTH-TENANT-001/002 was marked `partial` rather than `not-applicable` on that basis. A later
pull request removed the call site and the now-fully-dead query functions it was the only caller of;
AUTH-TENANT-001/002 is `not-applicable` again, see the Stage 5 detail section below.

IDOC's TOTP remembered-device subsystem is now an offered, opt-in feature. Server-owned policy
configuration gates it; the post-TOTP production action issues the hardened cookie and persisted digest;
the primary-login path validates it; and authenticator replacement invalidates it. AUTH-REMEMBER-001
through AUTH-REMEMBER-004 are therefore verified. Deployed enablement and secret values remain an
external production-configuration check, not repository evidence.

## Most consequential gaps (do not soften)

1. **Unverified residual production data in `idoc.team_members`/`idoc.teams`/`idoc.activity_logs.ip_address`**
   — **operational, not a code gap** (a Codex review on the pull request that removed the corresponding
   dead code paths caught this). The original SaaS-starter template wrote to all three
   (`db.insert(teamMembers)` and `logActivity()`'s `ip_address` field) until commit `a3192f1` removed
   that code, and `docs/08`'s own status line records "raw subscription starter deployed" as a real past
   state, not a hypothetical one. Whether the production database actually holds residual rows from that
   period — potentially real team-member names/emails or real IP addresses — cannot be determined from
   repository state. **Before any production-readiness claim, run a direct read-only query against the
   production database** (`select count(*) from idoc.team_members`, `select count(*) from
   idoc.activity_logs where ip_address is not null`) and, if either returns non-zero, treat the result as
   real user data requiring its own assessment (retention/purpose/notification), not as evidence the code
   fix was insufficient — the code fix is complete and verified independently of this question.
2. **AUTH-OPERATIONS-006 (alert correlation/anomaly detection)** — `partial`. A real severity
   taxonomy now exists and every existing admin-email alert's subject is tagged with it, but no
   correlation/anomaly-detection engine exists — each alert still fires independently, with no
   pattern or frequency detection across events.

The strongest, most genuinely verified items across all five stages: session-registry replay defense
(AUTH-SESSION-002/009/010, directly proven by dedicated e2e tests including one added by this program's
own legacy-session-removal PR), TOTP/recovery-code replay and concurrency defense (AUTH-MFA-006, passkey
sign-count regression defense), password storage (Argon2id, AUTH-STORAGE-004), OAuth transaction/state/
PKCE binding (AUTH-TRANSACTION-010, AUTH-OAUTH-002), audit-log DB-level immutability via trigger
(AUTH-AUDIT-002), and fail-closed production configuration validation (AUTH-OPERATIONS-009).

## Stage 5 — OAuth, Invitation, Tenant, Authorization

### IDOC tenancy/invitation model (Stage 5 detail)

IDOC is a **single-tenant, single-application** platform (one Vercel deployment, one Postgres schema `idoc`, docs/07 §15 "one Vercel-hosted Next.js deployment"). There is no organization/tenant entity anywhere in `lib/db/schema.ts` used as an authorization boundary; `application_roles` is a flat per-user role grant (`member` | `administrator` | `super_admin`, enforced by DB CHECK `application_roles_role_check`) with no scoping column. There is **no invitation flow of any kind**: the `invitations` table and `'invite-privileged-user'`/`ActivityType.INVITE_TEAM_MEMBER` enum values are genuinely unreferenced dead code (`grep` confirms zero call sites outside `lib/db/schema.ts` and the type definitions themselves). Administrator/Super Admin accounts are instead provisioned by an existing Super Admin calling `grantApplicationRole` (`lib/membership/role-grants.ts`) directly against a known user — this is documented, deliberate policy (docs/05 §4, docs/07 §11) requiring Super-Admin authorization + fresh TOTP step-up (`change-privileged-permissions`), not an omitted invitation feature. This makes AUTH-INVITE-001/002/003 **not-applicable**.

**Correction (this revision, per Codex review P1 finding on this PR):** the `teams`/`team_members` tables are **not** fully dead code as an earlier draft of this row claimed. `app/layout.tsx:31-32` calls `getTeamForUser()` (`lib/db/queries.ts:90-117`) inside the root layout's `SWRConfig` `fallback` prop on every request — a live server-side query against `idoc.team_members`/`idoc.teams`, scoped to `teamMembers.userId = <requesting user>`, whose result is serialized into the initial page payload for hydration regardless of whether any component actually subscribes to `/api/team` (the route itself does unconditionally return 404, but the layout-level SWR fallback is a separate, real code path that bypasses it). No production code path ever inserts a row into `team_members` — only `lib/db/seed.ts`, a local/dev seed script, does — so for any real signed-up user this query currently returns `null` and nothing is exposed today.

# 0. Purpose and method

This document is the authoritative control-by-control traceability matrix for every authentication, authorization, account-security, session-security, identity, MFA, password, OAuth, CSRF, rate-limit, account-state, cookie, and security-header behavior currently implemented in this repository. It exists so that:

1. every implemented control is documented somewhere, and this matrix says where;
2. every documented control is traceable to real code, and this matrix says where, or says plainly that it is not yet implemented;
3. every control is described precisely enough (mechanism, not adjective) that it can be mapped one-to-one to an automated test, existing or still-needed;
4. stale, contradictory, or aspirational claims found in other documents during this review are corrected at the source and cross-referenced here.

**Method.** Each control below was verified by reading the actual call chain (route/action → validation → session/auth lookup → authorization decision → database interaction → response/cookie mutation), not by trusting a function name or an existing document's claim. Where this review found the code and an existing document disagreed, the code's actual behavior is what is recorded as "Behavior," and the document is corrected elsewhere in this pull request; the disagreement itself is recorded in [§8](#8-documentation-corrections-made-by-this-review).

**Scope boundary.** Payment, subscription, and billing-abuse behavior (Stripe checkout, webhooks, manual payments, reconciliation) is out of scope except where it crosses an authentication or authorization boundary (for example, `requireAccountAccess('billing_boundary')` gating the Stripe Checkout entry point is in scope; Stripe webhook idempotency itself is not).

**Status vocabulary** used in the "Status" column:

- **Implemented** — the code implements the described behavior, and it is documented somewhere in `docs/`.
- **Implemented (was undocumented)** — the code implements the described behavior; no prior document described it precisely, or at all. This pull request adds the documentation via this matrix.
- **Partially implemented** — the described behavior holds for some but not all of its intended surface (the exact boundary is stated in the row).
- **Documented but not implemented** — an existing document claims this behavior; code does not yet provide it. Recorded as a gap, not silently removed from the record.
- **Contradictory (corrected)** — two or more existing documents (or one document and the code) disagreed; this review resolved the contradiction against the code and corrected the stale document in this pull request.

**Canonical reference baseline.** Per `docs/13-canonical-auth-reference-retrofit.md`, the canonical authority for what a correct implementation should look like is `marceloATpixelsmith/pixelsmith-auth-reference` contract `2.0.0` / machine schema `14.0.0` / validator `11.0.0` / mapping schema `1.0.0` / portable-config schema `2.0.0`. This matrix inventories IDOC's *actual current implementation*, which docs/13 already tracks against that baseline; it does not re-derive canonical requirements independently. Where docs/13 lists something as still-remaining reference-adoption work, that status is carried into this matrix rather than contradicted.

**Current authoritative status source.** This document's own per-requirement rows use IDOC's local
`AUTH-*` numbering, which only coincidentally matches canonical IDs at low numbers and has not been kept
in 1:1 sync with the canonical requirement list as it has grown. `docs/22-canonical-auth-evidence-matrix.md`
is a from-scratch, canonical-ID-keyed evidence matrix built directly against the current canonical
contract; treat it as the current authoritative status source for every canonical `AUTH-*` requirement,
and treat this document's per-requirement status claims below as historical narrative and descriptive
detail (cookie attribute table, CSRF/rate/header/Turnstile/config/log/DB/supply-chain notes, and the
pull-request changelog in §8) rather than current status.

**Answering the review questions directly, for this section:**
- *Can a correctly signed JWT be accepted if its persisted session row is missing?* No (AUTH-SESSION-002).
- *Can a revoked session be replayed?* No, proven behaviorally (AUTH-SESSION-007).
- *Can a session survive a `sessionVersion` increment?* No — the next `getUser()` call rejects it (AUTH-SESSION-003, AUTH-SESSION-008), proven both by a real DB-level increment (`tests/account-token-lifecycles.integration.ts`) and, now, by a live HTTP request with a forged JWT claiming a stale `sessionVersion` against a real registry row (`tests/security-e2e/session-replay.spec.ts`).
- *What happens at idle/absolute expiration?* `verifyToken()` throws; `getSession()` returns `null`; `middleware.ts` redirects `/dashboard/*` to `/sign-in` and clears the cookie (AUTH-SESSION-004/005). The expiry is a "the row ages out" event, not an explicit registry revocation with a reason.
- *Are timestamps trusted from the JWT or verified against persisted data?* Both: the JWT's own claims are internally sanity-checked (`assertSessionFresh`), and separately the persisted registry row's `authenticatedAt`/`absoluteExpiresAt` must exactly match the JWT's claims (AUTH-SESSION-002) — the database row, not the JWT alone, is authoritative.
- *Can a pending-auth or MFA-stage cookie be confused with a real session?* No (AUTH-SESSION-014).

## 8g. Changes made by the Google OAuth failure logging/alerting pull request (this revision)

This section records a small operational-visibility fix discovered while diagnosing a real production configuration issue during initial Google Sign-In setup: `app/api/auth/google/start/route.ts` and `app/api/auth/google/callback/route.ts` caught every failure silently -- the user saw a generic "Google authentication could not be completed" message, and nothing was recorded server-side at all, so there was no way to tell a benign outcome (a not-yet-linked account) apart from a real misconfiguration (a bad redirect URI, a stale env var) without adding print-debugging by hand.

1. **`lib/notifications/google-oauth-failure-alert.ts` (new file).** `notifyWebmasterOfGoogleOauthFailure` follows the same pattern as `breached-password-alert.ts`: best-effort, never throws, skips silently when `IDOC_ADMIN_NOTIFICATION_EMAIL` is unconfigured, and never includes the OAuth `code`/`state`/cookie/token values -- only a categorical failure reason and the current request's correlation ID (§8f), so an operator can jump straight to the matching Vercel function-log line. **Rate-limited by origin** (`checkOriginRateLimit('google_oauth_failure_alert', origin)`, the same primitive `start/route.ts` already used): `/api/auth/google/callback` is a public, unauthenticated GET route with no rate limit of its own, so without this an anonymous caller could repeatedly hit it with no state/binding cookie and force an email send on every single request, flooding the paid mail sender and the operations mailbox and burying genuine alerts under attacker-triggered noise -- caught in review (see the pull request's review history) before merge. Every failure is still logged unconditionally regardless of this limit; only the *email* is throttled. **Delivery is bounded to a 5-second timeout** (`AbortSignal.timeout`, threaded through a new optional `options.signal` parameter on `sendTransactionalEmail` that defaults to unbounded so no existing caller's behavior changes) so a slow/unresponsive Mailchimp can never block the caller's own failure redirect long enough to risk a serverless timeout. **The rate-limit preflight itself (`requestOrigin`/`checkOriginRateLimit`) runs inside the same guarded `try` block as delivery, not before it** -- a second review-round finding: those two calls depend on `RATE_LIMIT_HASH_KEY` and a real database write, either of which can throw on misconfiguration or a database outage, which would otherwise have escaped this "never throws" helper and broken the caller's own OAuth redirect exactly the way the original P1 finding described, just via a different trigger (a dependency failure instead of attacker volume). **A third review-round finding went further: catching that preflight isn't enough if it merely hangs rather than throwing** -- `lib/db/drizzle.ts` configures no statement timeout, so a slow/unavailable Postgres could leave `checkOriginRateLimit`'s awaited query pending well past the 5-second `AbortSignal.timeout` that only bounded the Mailchimp `fetch`. The whole preflight-and-delivery operation (`deliverAlert`) is now wrapped in a small `withDeadline` helper -- a `Promise.race` against a 5-second timer -- so the caller stops waiting and returns its own redirect on schedule regardless of which step is slow; `Promise.race` cannot cancel the underlying database query itself, but letting the caller move on is what the "never blocks the caller" contract actually requires.
2. **`app/api/auth/google/start/route.ts`, `app/api/auth/google/callback/route.ts`.** Every unexpected failure path now logs via `logError` (`google_oauth_start_failed`/`google_oauth_callback_failed`) with a categorical `reason` and also calls the new alert. `lib/auth/google-oidc-reference.ts`'s existing `GoogleOidcError.code` (`configuration`, `invalid_request`, `invalid_transaction`, `expired_transaction`, `provider_error`, `token_exchange_failed`, `invalid_id_token`) is reused directly as that categorical reason rather than inventing a parallel taxonomy. The callback route's binding-cookie check (the one most likely to fire during initial setup, since it's the very first check on the return leg) is now also logged/alerted rather than failing silently. **The start route's pre-existing rate-limit rejection is logged too** (`logWarn`, reason `rate_limited`) -- a fourth review-round finding: this early return predates the pull request and was left completely unlogged, contradicting this document's own "every failure path" claim; it deliberately does not alert, since routine throttling (e.g. many members behind one institutional NAT) is expected behavior, not an incident, but it must not be silently invisible to an operator trying to explain a real user's "failed" report.
3. **Alert suppressed for three expected, benign outcomes**, so normal usage doesn't page an operator: `GoogleAccountLinkRequiredError` (the account genuinely isn't linked yet -- a real business rule), `GoogleAccountNotEligibleError` (the account isn't eligible for Google sign-in), and a user simply declining Google's consent screen. The third one needed its own fix: `completeGoogleOidcCallback` maps every non-empty `error` query parameter -- including the standard OAuth2 `access_denied` Google sends on a declined consent -- to the same `GoogleOidcError('provider_error')`, which the classifier would otherwise alert on for an entirely ordinary user action; the callback route now reads the raw `error` query parameter directly (never trusted for anything security-relevant, only used to distinguish this one case) to tell a routine cancellation apart from an actual provider-side failure. All three are still logged (so they're visible in a log search), just not emailed. Every other failure -- any other `GoogleOidcError`, the binding-cookie check, and any other unexpected exception -- both logs and alerts.

**Judgment call, stated explicitly:** this is intentionally narrower than a full APM/error-tracking integration (still out of scope per §8f/§12) -- it targets the one flow that had zero visibility and a real, immediate operational need (diagnosing first-time Google OAuth setup), not a general-purpose unhandled-error reporter for the whole application. Extending the same alert-on-failure pattern to other auth flows should be a deliberate, scoped decision each time (what counts as "expected" vs. "alert-worthy" differs per flow), not a blanket default.

## 8i. Changes made by the legacy-session-removal pull request (this revision)

This section records what changed in the follow-up pull request that removed the legacy pre-registry session cookie's authentication acceptance path -- a control this document previously recorded as **AUTH-SESSION-009: Implemented**, describing deliberate, documented "one-way compatibility" behavior rather than a defect. A subsequent production-readiness review of this repository against the canonical `pixelsmith-auth-reference` (`AUTH-DEPENDENCY-002`: "Unavailable authoritative stores MUST not fall back to client claims, cookie-only sessions, stale privilege...") concluded that the accepted design still let a signed JWT alone establish authentication authority for the legacy code path, contrary to the canonical invariant, and asked for it to be removed as a hard security fix rather than left as an accepted, documented tradeoff.

1. **`lib/auth/session-tokens.ts`.** `normalizeSessionPayload` no longer reinterprets a payload short of the exact version-2 shape (`version:2`, `sessionId`, `authenticatedAt`, `lastActivityAt`, `absoluteExpiresAt`, plus `user:{id,sessionVersion}`) as a synthesized "legacy compatibility" session. Any other shape -- including the pre-retrofit starter-template `{user, iat}` payload this module previously accepted -- now throws `Unsupported session payload.` immediately, the same rejection an already-unsupported shape produced before this change. The removed branch previously synthesized a `sessionId` of the form `legacy-${iat}-${userId}` that was never written by `registerSession()`, so nothing downstream could ever revoke a session admitted through it.
2. **`lib/auth/session.ts`.** `getSession()` no longer has a second, un-registry-checked return path for the legacy cookie: it now reads only the canonical cookie and, when present, unconditionally requires `registeredSessionIsValid()` to return true (exactly the check every canonical session already had to pass) before returning a session. `LEGACY_SESSION_COOKIE_NAME` remains imported and used, but only for the pre-existing defensive `cookieStore.delete(...)` calls in `setSession`/`clearSession` -- never for reading a value.
3. **`middleware.ts`.** `canonicalCookie ?? legacyCookie` is gone; only `canonicalCookie` is ever verified, used to gate `/dashboard/*`, or refreshed. The legacy cookie is still looked up, but solely so every response path (redirect-to-sign-in, pass-through, refreshed-session, and the verification-failure branch) can defensively delete it via a small `finish()` wrapper -- previously that deletion only happened in the catch block, so a request carrying *only* a legacy cookie (no canonical cookie at all) would leave it sitting unswept on the success/pass-through paths.
4. **Why this was safe to remove outright, not phase out behind a bounded migration:** `setSession()` has never issued the legacy cookie name or shape since the persisted-session-registry retrofit (`auth/persisted-session-registry`, `auth/canonical-session-lifecycle`) landed on `main`; nothing else in the repository writes it (verified by a full-repository grep, not assumed). The absolute session lifetime is a fixed 12 hours (`SESSION_ABSOLUTE_SECONDS`) computed from the token's own `iat`, so any session that legitimately predates that retrofit already expired on its own terms days before this pull request, independent of this code change. There is therefore no currently-valid legacy session this change could invalidate -- the task's own conditional bounded-migration escape hatch ("if evidence shows active production compatibility still genuinely requires legacy sessions...") does not apply here, and forcing one anyway would just reintroduce, on a timer, the exact fallback being removed.
5. **Tests.** `tests/session-token-boundaries.test.ts`: the previous test documenting the fallback as verified, intended behavior was replaced with two rejection tests (the same malformed-version payload, and the actual bare `{user, iat}` starter-template shape). `tests/persisted-session-registry.test.ts` and `tests/canonical-session-lifecycle.test.ts`: source-inspection assertions rewritten to match the new `getSession()`/`middleware.ts`/`normalizeSessionPayload` structure and to assert the *absence* of the removed fallback rather than its presence. `tests/security-e2e/session-replay.spec.ts`: a new behavioral test forges the actual legacy cookie name and shape, signs it with the real `AUTH_SECRET` against a real, existing user, and proves it authenticates neither `/api/user` nor `/dashboard` (a 302 to `/sign-in`) against the live running app and real Postgres -- not just a source-inspection or pure-function proof.

**Judgment call, stated explicitly:** this document previously treated the legacy-cookie fallback as an accepted design tradeoff (AUTH-SESSION-009: Implemented, not a recorded gap). This pull request does not treat that as a documentation error to quietly correct -- it is recorded here as a genuine security-posture change: a control this repository's own records considered acceptable is now judged, against the canonical contract's authoritative-storage invariant, not to have been. Future review of this repository should not assume every row marked "Implemented" in earlier revisions of this document remains the intended design; §8i exists specifically so this reversal has a visible paper trail rather than a silently rewritten row.

## 8j. Changes made by the password-length Unicode-code-point pull request (this revision)

This section records a small, isolated correctness fix found while reviewing this repository's password policy against the canonical `pixelsmith-auth-reference` contract's `AUTH-PASSWORD-002` ("Password content fidelity... values beyond safe limits MUST be explicitly rejected and client/server length behavior MUST agree").

1. **`lib/auth/password-policy.ts`.** Added `countPasswordCharacters(value)` (`Array.from(value).length`, matching the canonical reference's own identically-named, identically-implemented helper), and switched every length check -- the client-facing `PASSWORD_REQUIREMENTS` minimum-length test and the server-side `passwordSchema`'s minimum and maximum -- from `String.prototype.length` (UTF-16 code units) to it. `zod`'s built-in `.min()`/`.max()` string checks operate on `.length` internally, so both were replaced with `.refine()` calls using the new function; the produced `ZodIssue` shape and messages are unchanged, so no caller needed to change how it reads validation errors.
2. **`components/auth/password-create-step.tsx`.** The client component's separate `tooLong` check (used only for the "128 characters or fewer" overflow message, since `PASSWORD_REQUIREMENTS` itself only carries a minimum-length rule) now also calls `countPasswordCharacters` instead of reading `.length` directly, so client and server length behavior stay in agreement exactly as the canonical requirement demands.
3. **The concrete defect this closes:** a password composed partly of astral-plane Unicode characters (many emoji, some scripts, e.g. mathematical alphanumeric symbols) is represented in JavaScript as one UTF-16 surrogate pair per character -- two `.length` units for one real character. That inflation worked in both directions: a password with as few as 6 real characters could reach a `.length` of 12 and wrongly pass the minimum-length check, and a legitimate password with 128 or fewer real characters could reach a `.length` over 128 and be wrongly rejected at the maximum. Neither direction was a full authentication bypass on its own (every other composition rule still had to be satisfied independently), but both were a real, user-visible divergence from the documented and canonically-required policy -- and the under-count direction is the security-relevant one, since it let genuinely weaker (shorter) passwords through the stated 12-character floor.
4. **`lib/auth/password-policy.ts` (added during review).** A Codex review finding on this pull request caught that the fix above only reached password *creation* (`passwordSchema`, used by signup/reset/change) -- every credential-*entry* boundary (`app/(login)/actions.ts`'s `signInSchema.password`, `updatePasswordSchema.currentPassword`, `deleteAccountSchema.password`; `app/(dashboard)/dashboard/security/actions.ts`'s `currentPasswordSchema.currentPassword`) still used a plain `z.string().min(1).max(128)`, i.e. the same raw-`.length` bug on the *verification* side. A user who legitimately created a ≤128-code-point password containing enough astral-plane characters to push its UTF-16 length past 128 would have been rejected by these entry schemas before `comparePasswords` ever ran -- a real, self-inflicted lockout, not merely a creation-time inconvenience. Added `passwordEntrySchema` (still bounded at `MAX_PASSWORD_LENGTH`, still counted in code points via `countPasswordCharacters`, but with no composition requirements and no 12-character minimum, since it verifies an existing credential exactly as created rather than creating a new one) and routed all four call sites through it.
5. **Tests.** `tests/password-composition-policy.test.ts` gained a direct unit test of `countPasswordCharacters` against a known surrogate-pair character, adversarial passwords for both `passwordSchema` and `passwordEntrySchema` constructed to be misjudged by the old `.length`-based check in each direction, and tests proving `passwordEntrySchema` deliberately does not enforce composition or the minimum. `tests/password-guidance-ux.test.ts`'s source-inspection assertion was updated to match the new call site.

No migration, no compatibility impact on any existing password (every existing password was already validated and hashed under the old, still-passing-for-ASCII-passwords check; this only changes behavior for the narrow set of passwords containing astral-plane Unicode characters, which is a strict correctness improvement, not a new restriction on any password that was correctly accepted before).

## 8k. Changes made by the account-authentication-suspension pull request (this revision)

This section records the fix for the canonical `AUTH-LIFECYCLE-006` gap recorded in `docs/22`: `idoc.users.account_state` already had a `suspended` value in its DB CHECK constraint (migration `0024`), and every authorization boundary (`mayAccessAccountFunction`, `signIn`) already hard-denied that state -- but nothing anywhere ever *set* it. An administrator had no way to stop a compromised or abusive account from authenticating short of the member deleting their own account.

1. **`lib/membership/account-suspension.ts` (new).** `suspendUserAccount(userId, reason)` and `reinstateUserAccount(userId, {accountState, reason})`, both `requireAccountAccess('administration')` + `requireAdministrator`-gated. Suspension locks the target row, rejects a user already suspended/deleted/unverified, rejects a user who currently holds an `administrator`/`super_admin` grant (privilege removal must go through `revokeApplicationRole` first -- otherwise an Administrator could use suspension as a side channel to disable a Super Admin's account while leaving their role grant, and its authority the moment the account is reinstated, intact underneath), sets `account_state='suspended'`, bumps `session_version`, and writes an audit entry -- all in one transaction. Outside the transaction it revokes every active `idoc.auth_sessions` row and every `idoc.login_trusted_devices` row for the target user (deliberately via `revokeLoginDeviceTrustForUser`, the DB-only variant, not `forgetAllLoginDevices`: the latter also clears a cookie on the *current* response, which for an admin acting on someone else's account would be the admin's own browser, not the target's) and enqueues an `account_suspended` security notification. Reinstatement requires the admin to explicitly choose the restored `account_state` (`active`/`onboarding`/`migrated_pending`, mirroring `reinstateMembership`'s existing pattern) rather than the system guessing what it was before suspension.
2. **`lib/db/migrations/0028_account_suspension_notification_kinds.sql` (new).** Adds `'account_suspended'`/`'account_reinstated'` to `auth_security_notification_outbox`'s `kind` CHECK constraint, following the exact pattern of migrations `0025`/`0027`. `AUTH_SECURITY_KINDS` (`lib/notifications/auth-security-events.ts`) and the delivery content map (`lib/notifications/auth-security-delivery.ts`) were updated to match.
3. **`app/(dashboard)/admin/members/actions.ts` / `account-suspension-form.tsx` / `page.tsx`.** A new "Account authentication" section on the admin member page, distinct from and below the existing "Membership status" section, explicitly labeled to avoid the two suspension concepts (club-entitlement vs. authentication) being confused by an operator.
4. **Tests.** `tests/account-suspension.integration.ts` (new, real Postgres): suspending an active account sets state/session-version/revokes sessions and devices/writes audit and notification; suspending an already-suspended, deleted, or unverified account is rejected; suspending a user who holds an active role grant is rejected; a non-administrator cannot suspend or reinstate; reinstating restores the chosen state without bumping `session_version`; reinstating a non-suspended account is rejected. `tests/authorization-boundary-inventory.test.ts` and `tests/database-integration.integration.ts` updated for the new Server Actions and migration.
5. **Two Codex review findings on this same pull request, both fixed.**
   - **A real concurrency race.** `grantApplicationRole` inserted into `application_roles` (a table `suspendUserAccount`'s transaction never locks) before touching `users`; a grant and a suspension of the same target could interleave so suspension's read of `application_roles` missed the grant's not-yet-committed insert, suspension committed, and the grant's own `users` update then proceeded once suspension's lock released -- leaving a suspended account with an active administrator/Super Admin grant underneath. Fixed by having `grantApplicationRole` take the same `users` row lock, and reject a suspended/deleted target, before touching `application_roles` at all -- the two operations are now mutually exclusive on the same user. `tests/role-grants.integration.ts` gained a real concurrent-race test (via the existing `concurrently()` harness helper) asserting the DB never ends up in the inconsistent state, plus a direct test that granting a role to an already-suspended/deleted account is rejected.
   - **Retry-unsafe partial failure.** If the session/device revocation or notification-enqueue step (both deliberately outside the state-transition transaction) failed after that transaction committed, retrying the same admin action was rejected outright ("already suspended" / "not currently suspended"), with no way to complete the still-missing work -- and the notification's dedupe key was keyed on call-time `Date.now()`, so even a successful retry would have enqueued a duplicate notification rather than converging. Fixed: both functions now treat "the account is already in the state this call would have produced" as a successful idempotent retry rather than an error, still (re-)running the side effects (both are independently idempotent -- session/device revocation only touches not-yet-revoked rows), and the notification dedupe key is now derived from the DB-committed transition timestamp rather than wall-clock call time. `tests/account-suspension.integration.ts` gained tests for both directions, each asserting exactly one audit row and exactly one notification row survive a retry.

No compatibility impact on existing users: `suspended` was already a valid, already-enforced `account_state` value; this only adds a way to reach it and back out of it, both audited and notified.

# 12. Residual risks that cannot be completely validated by repository automation

1. **CSRF on Server Actions (AUTH-CSRF-001) — closed in a later pull request.** Next's built-in Origin-mismatch check plus `middleware.ts`'s own rejection of an absent-Origin Server Action POST (mirroring Next's own request-detection logic exactly) together cover this application's entire mutation surface, all of which is Server Actions. What remains genuinely outside this repository's control is browser/CDN/reverse-proxy behavior that could strip or rewrite the `Origin` header before it reaches the application — a platform-trust assumption every Origin-based CSRF defense shares, not a gap specific to this implementation.
2. **The legacy single-bucket rate limit on the token/link-based account-recovery path was a real, live gap — closed in this pull request** (AUTH-RATE-002 now Implemented). Kept here as a record of what was true prior to this revision, not a currently-open risk.
3. **A correlation-ID now exists (AUTH-LOG-004); a full APM integration still does not.** An actual production incident investigation can now grep application logs for one `x-request-id` and see everything a single request's runtime logging did (with the one documented `password-breach-check.ts` exception, per §8f), on top of `audit_log` timestamps and categorical evidence. This narrows the gap but does not close it: there is still no distributed tracing across external calls (the database, the email/breach-check/Stripe providers), no error aggregation/alerting dashboard, and no automatic correlation between a client-side crash report and the specific server request that triggered it beyond both being logged with their own IDs. A full APM/error-tracking vendor integration (Sentry or similar) remains genuinely out of scope: it requires provisioning a vendor account and credentials this repository cannot do for itself.
4. **Production secret deployment and operator UAT remain outstanding release gates** per `docs/07` §15.5–15.6, independent of how complete the *code* is — repository readiness is not deployment readiness, and this matrix inventories the former only.
5. **Real Google provider trust establishment (JWKS/token exchange) is not exercised by this repository's automation** (AUTH-OAUTH-007) — every OAuth adversarial test in this pull request exercises the repository-controlled transaction/purpose/replay/linking logic against real PostgreSQL without contacting Google, per this document's own testing principles; the actual cryptographic trust handshake with Google remains external-provider residual assurance, consistent with `docs/20`'s existing scope boundary.
6. **The `lib/db/drizzle.ts` Proxy defect fixed in the prior pull request (AUTH-DB-005) was latent in production before that review** — its existence for an unknown period is itself informative: Google OAuth login/signup and the security-notification outbox worker may have been non-functional in any environment that actually exercised them before that fix, which repository automation alone cannot retroactively confirm or deny for a real deployed history.
7. **The password-breach check (AUTH-PASSWORD-006) deliberately fails open on provider unavailability** — a real, accepted availability-over-strictness tradeoff: if HaveIBeenPwned's range API is unreachable, a genuinely breached password can still be accepted (with a categorical warning logged), rather than blocking every signup/reset in the repository until a third party this application does not control recovers. This is a considered design choice, not an oversight, but it does mean the check's real-world effectiveness during a provider outage is lower than its test coverage alone would suggest.
8. **The dependency-vulnerability CI gate (AUTH-SUPPLY-001) only hard-fails on critical advisories.** A follow-up pull request closed the `drizzle-orm` and three Next.js-specific advisories that had a safe, narrow fix (see AUTH-SUPPLY-001). Eight advisories remain reported-but-not-blocking; each was individually assessed for real-world exploitability in *this application's actual code paths*, not just the advisory's abstract existence:
   - **`sharp` (libvips) vulnerabilities and the Next.js Image Optimizer `remotePatterns` DoS (GHSA-9g9p-9gw9-jx7f)** — both require `next/image` or an image-upload/transform feature to be reachable. This app has zero `next/image` usage and no file/image-upload feature anywhere in the codebase (verified by direct search). Not exploitable via any route this app serves.
   - **`postcss` XSS-via-unescaped-`</style>` and path-traversal/arbitrary-file-read advisories (bundled inside `next`, not a direct dependency)** — postcss here only ever processes this repository's own developer-authored CSS at build time; it never runs against attacker-supplied CSS or file paths at request time. Not exploitable at runtime. Next.js has not updated its bundled postcss even in the newest 16.4.0 canary checked; a fix requires `next@16.3.3`+ (see below) or later.
   - **`esbuild` dev-server request/response disclosure (GHSA-67mh-4wv8-2f99)** — reached only via `drizzle-kit`'s transitive `@esbuild-kit` dependency, a local schema-migration dev tool never present in production, never exposed to the network beyond localhost during a developer's own `drizzle-kit` invocation.
   - **Playwright's "downloads and installs browsers without integrity verification"** — a `devDependencies`-only test-tooling advisory; not shipped, not present in production.

   None of these four is force-upgraded because doing so today would require a Next.js **major**-version migration (`15.x`→`16.x`, since the bundled `postcss` version has not moved even in 16.4.0-canary builds and the Image Optimizer fix lands at `>=16.1.5`) against code paths this app does not exercise — a disproportionate, real-regression-risk change for a currently-unreachable finding. Dependabot continues to open weekly PRs; if any of these four ever becomes reachable (e.g. `next/image` or an upload feature is added), it must be re-triaged as urgent at that point, not left on the same "not yet forced" footing.
9. **WebAuthn ceremony verification (AUTH-MFA-012/013) relies on `@simplewebauthn/server`'s correctness for CBOR/COSE attestation parsing and signature verification** — this repository's own tests exercise the surrounding orchestration (DB persistence, gating, audit/notification, sign-count replay handling) and one real end-to-end browser ceremony via a Chromium CDP virtual authenticator, but do not independently re-verify the cryptographic library's internal correctness against adversarial/malformed attestation objects, matching this document's existing treatment of `jose` (JWT) and `bcryptjs` (password hashing) as trusted external primitives rather than re-tested from first principles. The virtual authenticator used in the e2e test is a well-behaved, spec-compliant one; it does not exercise how the application responds to a malicious or buggy real authenticator.
10. **Only one physical class of authenticator (a Chromium CDP virtual authenticator simulating a platform authenticator) is exercised end-to-end** — cross-authenticator behavior (a real hardware security key, a different browser's implementation, synced-passkey provider quirks) is architecturally handled the same way by this implementation (device type and backup state are recorded but not treated as security-relevant, transports are stored for the browser's own use) but not separately tested per authenticator class.
11. General note: this matrix, like `docs/20`, does not constitute penetration-test certification, and passing every test referenced here does not mean the deployed system is "secure" — it means the specific, named invariants above hold against the specific, named tests above.

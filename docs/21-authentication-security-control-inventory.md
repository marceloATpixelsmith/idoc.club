# 0. Purpose and method

This document is the historical implementation inventory and detailed design narrative for
authentication, authorization, account security, sessions, identity, MFA, passwords, OAuth, CSRF,
rate limits, account states, cookies, and security headers. `docs/22-canonical-auth-evidence-matrix.md`
is the authoritative current canonical-control status source, and
`docs/23-auth-security-remediation-backlog.md` is the authoritative current gap list. This document
exists so that:

1. every implemented control is documented somewhere, and this matrix says where;
2. every documented control is traceable to real code, and this matrix says where, or says plainly that it is not yet implemented;
3. every control is described precisely enough (mechanism, not adjective) that it can be mapped one-to-one to an automated test, existing or still-needed;
4. implementation history remains available without overriding the newer evidence audit.

**Method.** Each control below was verified by reading the actual call chain (route/action → validation → session/auth lookup → authorization decision → database interaction → response/cookie mutation), not by trusting a function name or an existing document's claim. Where this review found the code and an existing document disagreed, the code's actual behavior is what is recorded as "Behavior," and the document is corrected elsewhere in this pull request; the disagreement itself is recorded in [§8](#8-documentation-corrections-made-by-this-review).

**Scope boundary.** Payment, subscription, and billing-abuse behavior (Stripe checkout, webhooks, manual payments, reconciliation) is out of scope except where it crosses an authentication or authorization boundary (for example, `requireAccountAccess('billing_boundary')` gating the Stripe Checkout entry point is in scope; Stripe webhook idempotency itself is not).

**Status vocabulary** used in the "Status" column:

- **Implemented** — the code implements the described behavior, and it is documented somewhere in `docs/`.
- **Implemented (was undocumented)** — the code implements the described behavior; no prior document described it precisely, or at all. This pull request adds the documentation via this matrix.
- **Partially implemented** — the described behavior holds for some but not all of its intended surface (the exact boundary is stated in the row).
- **Documented but not implemented** — an existing document claims this behavior; code does not yet provide it. Recorded as a gap, not silently removed from the record.
- **Contradictory (corrected)** — two or more existing documents (or one document and the code) disagreed; this review resolved the contradiction against the code and corrected the stale document in this pull request.

**Canonical reference baseline.** Per `docs/13-canonical-auth-reference-retrofit.md`, the canonical authority for what a correct implementation should look like is `marceloATpixelsmith/pixelsmith-auth-reference` contract `2.0.0` / machine schema `14.0.0` / validator `11.0.0` / mapping schema `1.0.0` / portable-config schema `2.0.0`. This matrix inventories IDOC's *actual current implementation*, which docs/13 already tracks against that baseline; it does not re-derive canonical requirements independently. Where docs/13 lists something as still-remaining reference-adoption work, that status is carried into this matrix rather than contradicted.

**Current authoritative status source.** This document's own per-requirement rows use IDOC's local
`AUTH-*` numbering, which only coincidentally matches canonical IDs at low numbers and has not been kept
in 1:1 sync with the canonical requirement list as it has grown. `docs/22-canonical-auth-evidence-matrix.md`
is a from-scratch, canonical-ID-keyed evidence matrix built directly against the current canonical
contract; treat it as the current authoritative status source for every canonical `AUTH-*` requirement,
and treat this document's per-requirement status claims below as historical narrative and descriptive
detail (cookie attribute table, CSRF/rate/header/Turnstile/config/log/DB/supply-chain notes, and the
pull-request changelog in §8) rather than current status.

**Answering the review questions directly, for this section:**
- *Can a correctly signed JWT be accepted if its persisted session row is missing?* No (AUTH-SESSION-002).
- *Can a revoked session be replayed?* No, proven behaviorally (AUTH-SESSION-007).
- *Can a session survive a `sessionVersion` increment?* No — the next `getUser()` call rejects it (AUTH-SESSION-003, AUTH-SESSION-008), proven both by a real DB-level increment (`tests/account-token-lifecycles.integration.ts`) and, now, by a live HTTP request with a forged JWT claiming a stale `sessionVersion` against a real registry row (`tests/security-e2e/session-replay.spec.ts`).
- *What happens at idle/absolute expiration?* `verifyToken()` throws; `getSession()` returns `null`; `middleware.ts` redirects protected page families (`/dashboard`, `/admin`, and `/onboarding`, including their descendants) to `/sign-in` and clears the cookie when token verification itself fails. If a still-validly-signed cookie names a registry-revoked/stale session that middleware cannot detect, the protected Server Component boundary performs the authoritative `getUser()`/`requireAccountAccess()` check and likewise redirects the unauthenticated visitor to `/sign-in` (AUTH-SESSION-004/005, AUTH-SESSION-010, AUTH-AUTHZ-009). The expiry is a "the row ages out" event, not an explicit registry revocation with a reason.
- *Are timestamps trusted from the JWT or verified against persisted data?* Both: the JWT's own claims are internally sanity-checked (`assertSessionFresh`), and separately the persisted registry row's `authenticatedAt`/`absoluteExpiresAt` must exactly match the JWT's claims (AUTH-SESSION-002) — the database row, not the JWT alone, is authoritative.
- *Can a pending-auth or MFA-stage cookie be confused with a real session?* No (AUTH-SESSION-014).

## 8w. Changes made by the AUTH_SECRET-rotation pull request (this revision)

`docs/22`'s `AUTH-CRYPTO-005` row flagged that TOTP encryption keys genuinely support multi-key rotation, but session-key (`AUTH_SECRET`) rotation had no ring/overlap at all -- `lib/auth/session-tokens.ts` read a single value for both signing and verification, so rotating it was a hard cutover that invalidated every outstanding session cookie immediately, exactly as `docs/07` §15.1 previously documented ("No old-key ring exists, so coordinate a forced sign-in").

1. **`lib/runtime/configuration.ts`: new `authSecretRingForServer()`.** Optional `AUTH_SECRET_RETIRED_KEYS` (a JSON array of prior `AUTH_SECRET` values, each ≥32 characters); unset is exactly the prior single-key behavior, so no existing deployment needs any reconfiguration. When set, returns `[activeKey, ...retiredKeys]` with the current `AUTH_SECRET` always first and never duplicated.
2. **`lib/auth/session-tokens.ts`: `signToken` uses only the active (index 0) key; `verifyToken` tries every key in the ring in order, returning the first successful, still-fresh result.** A session signed under a retired key still verifies, and naturally re-signs under the new active key on its next activity refresh (`middleware.ts`), so a routine rotation no longer forces every user to sign in again. The five short-lived (≤15 minute) transient-authority call sites (`google-oauth-browser-binding.ts`, `google-identity-link-evidence.ts`, `pending-signup.ts`, `pending-login.ts`, `pending-password-reset.ts`) are deliberately left as a hard cutover on rotation -- restarting a 15-minute flow is a negligible cost, and folding all of them into the ring for a single call site's worth of benefit was unnecessary scope.
3. **`docs/07` §15.2: new two-path `AUTH_SECRET` rotation procedure.** A routine rotation (no suspected compromise) moves the old value into `AUTH_SECRET_RETIRED_KEYS` for a graceful overlap; a suspected-compromise rotation deliberately omits that step for the same immediate hard cutover as before. §15.1's `AUTH_SECRET` row and §12.2's post-restore reconciliation step 1 (which specifically wants the hard-cutover behavior) both now point at this procedure explicitly. **A Codex review finding on this pull request, fixed:** the hard-cutover procedure originally only said not to *add* the old value to `AUTH_SECRET_RETIRED_KEYS` -- it never said to *clear* entries a still-in-progress routine rotation might have already put there, which would let cookies signed under that older key keep verifying right through an "immediate" cutover. Both the hard-cutover procedure and §12.2's reconciliation step now explicitly say to clear `AUTH_SECRET_RETIRED_KEYS` entirely (unset or `[]`) as their first step.
4. **Tests.** `tests/runtime-configuration.test.ts`: the ring's default single-key behavior, ordering/deduplication, and fail-closed malformed/undersized input. `tests/session-token-boundaries.test.ts`: a token signed under a retired `AUTH_SECRET` still verifies once that value moves into `AUTH_SECRET_RETIRED_KEYS`, and is rejected again once fully dropped from the list (proving the hard-cutover option still works unchanged).

## 8x. Fix a genuine race in email-change verification (this revision)

`docs/22`'s `AUTH-EMAIL-003`/`AUTH-TRANSACTION-008` rows claimed the concurrent-email-claim race in `consumeEmailVerification` "resolved atomically," citing `tests/email-change.integration.ts`'s race test as proof. That claim was not accurate: the pre-commit existence check the row relied on (`SELECT ... FROM users WHERE email = ...`) is a plain read with no lock against a concurrent writer, so two members racing to claim the same address could both pass it before either transaction committed. The `idoc.users_email_unique` constraint then correctly let only one `UPDATE` through, but the loser's write raised an uncaught `PostgresError` (code `23505`) that propagated out of `db.transaction()` as an unhandled rejection -- a 500, not the `{status:'invalid'}` outcome the row and the test both expected. This surfaced as a genuine, intermittent CI failure (dependent on real transaction scheduling, not a flaky/infra issue) rather than as something found by inspection.

1. **`lib/membership/email-verification.ts`.** `consumeEmailVerification` now wraps the transaction call and catches exactly this case via a new `isEmailUniqueRaceViolation` helper -- `code === '23505'` scoped to `users_email_unique` or `users_normalized_email_unique` specifically, so no other, unrelated constraint violation is silently swallowed -- and returns `{status: 'invalid'}`, the same outcome the pre-commit check already produces for every other "someone else got there first" path. **Two Codex review findings on this pull request, both fixed:** (a) the pre-commit check compares against the already-lowercased `pendingEmail`, so it misses an existing member stored with different casing (schema.ts's `users_normalized_email_unique`, a `lower(email)` index, is a second, distinct constraint from `users_email_unique` -- both are now recognized); (b) drizzle-orm wraps the driver's `PostgresError` in its own error object with the original attached as `.cause` rather than always exposing `code`/`constraint_name` directly (confirmed by direct reproduction, not merely suspected), so the check now inspects both the caught error and its `.cause`. The transaction body itself is unchanged (extracted into `consumeEmailVerificationTransaction` only to make the try/catch boundary clean); no schema or migration change. A new regression test (`tests/email-change.integration.ts`) proves the mixed-case collision resolves to `{status:'invalid'}` deterministically, without needing real concurrency to reproduce.
2. **docs/22** (`AUTH-EMAIL-003`/`AUTH-TRANSACTION-008` notes corrected to record what was actually wrong and now fixed; both remain `verified`, since the underlying behavior is now genuinely what they always claimed).

# 11. Explicit exclusions from this inventory

- Stripe checkout, subscription, webhook-idempotency, manual-payment, and reconciliation behavior, except where it crosses an authentication/authorization boundary (the `billing_boundary` scope of `requireAccountAccess`, and the webhook's CSRF-exemption rationale, are the only payment-adjacent items included).
- CMS/seminar/news publishing authorization (Release 4–6 scope), which reuses the same `requireAccountAccess` primitives documented here but is not itself built yet.
- Deployed CDN/Vercel platform configuration, real provider/DNS behavior, secret rotation operations, and incident response — `docs/20` already states these require independent review beyond repository automation, and this matrix does not attempt to substitute for that review.
- Social-engineering and credential-stuffing resistance at realistic scale, non-Chromium browser behavior, dependency/infrastructure compromise, and novel chained business-logic attacks — same rationale as above.

# 12. Residual risks that cannot be completely validated by repository automation

1. **CSRF on Server Actions (AUTH-CSRF-001) — closed in a later pull request.** Next's built-in Origin-mismatch check plus `middleware.ts`'s own rejection of an absent-Origin Server Action POST (mirroring Next's own request-detection logic exactly) together cover this application's entire mutation surface, all of which is Server Actions. What remains genuinely outside this repository's control is browser/CDN/reverse-proxy behavior that could strip or rewrite the `Origin` header before it reaches the application — a platform-trust assumption every Origin-based CSRF defense shares, not a gap specific to this implementation.
2. **The legacy single-bucket rate limit on the token/link-based account-recovery path was a real, live gap — closed in this pull request** (AUTH-RATE-002 now Implemented). Kept here as a record of what was true prior to this revision, not a currently-open risk.
3. **A correlation-ID now exists (AUTH-LOG-004); a full APM integration still does not.** An actual production incident investigation can now grep application logs for one `x-request-id` and see everything a single request's runtime logging did (with the one documented `password-breach-check.ts` exception, per §8f), on top of `audit_log` timestamps and categorical evidence. This narrows the gap but does not close it: there is still no distributed tracing across external calls (the database, the email/breach-check/Stripe providers), no error aggregation/alerting dashboard, and no automatic correlation between a client-side crash report and the specific server request that triggered it beyond both being logged with their own IDs. A full APM/error-tracking vendor integration (Sentry or similar) remains genuinely out of scope: it requires provisioning a vendor account and credentials this repository cannot do for itself.
4. **Production secret deployment and operator UAT remain outstanding release gates** per `docs/07` §15.5–15.6, independent of how complete the *code* is — repository readiness is not deployment readiness, and this matrix inventories the former only.
5. **Real Google provider trust establishment (JWKS/token exchange) is not exercised by this repository's automation** (AUTH-OAUTH-007) — every OAuth adversarial test in this pull request exercises the repository-controlled transaction/purpose/replay/linking logic against real PostgreSQL without contacting Google, per this document's own testing principles; the actual cryptographic trust handshake with Google remains external-provider residual assurance, consistent with `docs/20`'s existing scope boundary.
6. **The `lib/db/drizzle.ts` Proxy defect fixed in the prior pull request (AUTH-DB-005) was latent in production before that review** — its existence for an unknown period is itself informative: Google OAuth login/signup and the security-notification outbox worker may have been non-functional in any environment that actually exercised them before that fix, which repository automation alone cannot retroactively confirm or deny for a real deployed history.
7. **The password-breach check (AUTH-PASSWORD-006) deliberately fails open on provider unavailability** — a real, accepted availability-over-strictness tradeoff: if HaveIBeenPwned's range API is unreachable, a genuinely breached password can still be accepted (with a categorical warning logged), rather than blocking every signup/reset in the repository until a third party this application does not control recovers. This is a considered design choice, not an oversight, but it does mean the check's real-world effectiveness during a provider outage is lower than its test coverage alone would suggest.
8. **High and critical dependency advisories are release blockers.** The fast PR workflow runs `pnpm audit --audit-level=high` without a warning-only escape, across production and CI tooling dependencies; the full authentication-security workflow relies on that shared gate rather than repeating it. `scripts/validate-toolchain-policy.mjs` also enforces the exact pnpm pin and blocking command. Dependabot remains enabled. A registry audit must pass on the final PR head; an unavailable registry is an environmental failure, never evidence of a clean dependency tree.
9. **Moot — removed.** This item covered `@simplewebauthn/server`'s CBOR/COSE attestation-parsing dependency risk (AUTH-MFA-012/013); passkey/WebAuthn support and that dependency were fully removed, so this residual risk no longer applies.
10. **Moot — removed.** This item covered cross-authenticator-class test coverage for WebAuthn; passkey/WebAuthn support was fully removed, so this residual risk no longer applies.
11. General note: this matrix, like `docs/20`, does not constitute penetration-test certification, and passing every test referenced here does not mean the deployed system is "secure" — it means the specific, named invariants above hold against the specific, named tests above.

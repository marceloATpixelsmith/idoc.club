# 0. Purpose and method

This document is the authoritative control-by-control traceability matrix for every authentication, authorization, account-security, session-security, identity, MFA, password, OAuth, CSRF, rate-limit, account-state, cookie, and security-header behavior currently implemented in this repository. It exists so that:

1. every implemented control is documented somewhere, and this matrix says where;
2. every documented control is traceable to real code, and this matrix says where, or says plainly that it is not yet implemented;
3. every control is described precisely enough (mechanism, not adjective) that it can be mapped one-to-one to an automated test, existing or still-needed;
4. stale, contradictory, or aspirational claims found in other documents during this review are corrected at the source and cross-referenced here.

**Method.** Each control below was verified by reading the actual call chain (route/action → validation → session/auth lookup → authorization decision → database interaction → response/cookie mutation), not by trusting a function name or an existing document's claim. Where this review found the code and an existing document disagreed, the code's actual behavior is what is recorded as "Behavior," and the document is corrected elsewhere in this pull request; the disagreement itself is recorded in [§8](#8-documentation-corrections-made-by-this-review).

**Scope boundary.** Payment, subscription, and billing-abuse behavior (Stripe checkout, webhooks, manual payments, reconciliation) is out of scope except where it crosses an authentication or authorization boundary (for example, `requireAccountAccess('billing_boundary')` gating the Stripe Checkout entry point is in scope; Stripe webhook idempotency itself is not).

**Status vocabulary** used in the "Status" column:

- **Implemented** — the code implements the described behavior, and it is documented somewhere in `docs/`.
- **Implemented (was undocumented)** — the code implements the described behavior; no prior document described it precisely, or at all. This pull request adds the documentation via this matrix.
- **Partially implemented** — the described behavior holds for some but not all of its intended surface (the exact boundary is stated in the row).
- **Documented but not implemented** — an existing document claims this behavior; code does not yet provide it. Recorded as a gap, not silently removed from the record.
- **Contradictory (corrected)** — two or more existing documents (or one document and the code) disagreed; this review resolved the contradiction against the code and corrected the stale document in this pull request.

**Canonical reference baseline.** Per `docs/13-canonical-auth-reference-retrofit.md`, the canonical authority for what a correct implementation should look like is `marceloATpixelsmith/pixelsmith-auth-reference` contract `1.10.0` / machine schema `13.0.0` / validator `10.0.0` / mapping schema `1.0.0` / portable-config schema `2.0.0`. This matrix inventories IDOC's *actual current implementation*, which docs/13 already tracks against that baseline; it does not re-derive canonical requirements independently. Where docs/13 lists something as still-remaining reference-adoption work, that status is carried into this matrix rather than contradicted.

**Answering the review questions directly, for this section:**
- *Can a correctly signed JWT be accepted if its persisted session row is missing?* No (AUTH-SESSION-002).
- *Can a revoked session be replayed?* No, proven behaviorally (AUTH-SESSION-007).
- *Can a session survive a `sessionVersion` increment?* No — the next `getUser()` call rejects it (AUTH-SESSION-003, AUTH-SESSION-008), though this specific end-to-end effect is currently proven only by source inspection plus a DB-level increment test, not a live "old JWT rejected after version bump" HTTP test (see §9 gap).
- *What happens at idle/absolute expiration?* `verifyToken()` throws; `getSession()` returns `null`; `middleware.ts` redirects `/dashboard/*` to `/sign-in` and clears the cookie (AUTH-SESSION-004/005). The expiry is a "the row ages out" event, not an explicit registry revocation with a reason.
- *Are timestamps trusted from the JWT or verified against persisted data?* Both: the JWT's own claims are internally sanity-checked (`assertSessionFresh`), and separately the persisted registry row's `authenticatedAt`/`absoluteExpiresAt` must exactly match the JWT's claims (AUTH-SESSION-002) — the database row, not the JWT alone, is authoritative.
- *Can a pending-auth or MFA-stage cookie be confused with a real session?* No (AUTH-SESSION-014).

# 12. Residual risks that cannot be completely validated by repository automation

1. **Application-level HSTS is not configured** (AUTH-HEADER-003). If the deployed environment does not independently guarantee HSTS (e.g. via Vercel platform defaults), the browser has no cached instruction to upgrade to HTTPS on a first/expired visit. This cannot be validated from the repository alone.
2. **No general CSRF token layer beyond Next.js's built-in Server Action origin check** (AUTH-CSRF-001). This is an accepted, already-documented (docs/13) open item, not a newly discovered one, but it remains unverified by any test in this repository and its real-world risk depends on browser/CDN behavior this repository cannot fully control or observe.
3. **The legacy single-bucket rate limit on the token/link-based account-recovery path** (AUTH-RATE-002) is a real, live gap in abuse resistance for that one path, independent of how well-tested the rest of the rate-limiting design is.
4. **No correlation-ID/flowId and no APM integration** (AUTH-LOG-004) means an actual production incident investigation depends entirely on `audit_log` timestamps and categorical evidence — sufficient for the invariants this repository tests, but not equivalent to full request tracing.
5. **Production secret deployment and operator UAT remain outstanding release gates** per `docs/07` §15.5–15.6, independent of how complete the *code* is — repository readiness is not deployment readiness, and this matrix inventories the former only.
6. General note: this matrix, like `docs/20`, does not constitute penetration-test certification, and passing every test referenced here does not mean the deployed system is "secure" — it means the specific, named invariants above hold against the specific, named tests above.

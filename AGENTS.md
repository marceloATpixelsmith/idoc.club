# Repository instructions

The Markdown files in `docs/` are the authoritative IDOC project documentation.

For every Codex implementation task, read and follow `docs/09-codex-working-rules.md`.

For every GPT collaboration task—including planning, writing Codex prompts, patching pull requests, handling CI or review feedback, and preparing a handoff—read and follow `docs/10-gpt-collaboration-rules.md`.

For every pull request, read `docs/26-ci-risk-classification-and-agent-merge-policy.md`. Classify the changed files before merging. The fast PR check is sufficient only for changes explicitly listed as low risk. If the policy requires a full workflow, run it against the current PR revision and do not merge until it passes.

For every task that merges into `main`, investigates a difference between `staging.idoc.club` and `redesign.idoc.club`, or otherwise touches deployment branches or environment configuration, read and follow the "Branch, environment, and deployment workflow" section of `docs/07-administrator-and-operations-runbook.md`.

When code changes membership rules, member fields, data structures, authorization, security, billing, migration, notifications, administration, operations, CMS access, seminars, news, or publishing, update the corresponding document in `docs/` in the same pull request. Keep `docs/08-product-roadmap-and-functional-requirements.md` aligned when scope, sequencing, or release gates change.

For any change to an administrator table, drawer or form, read and follow `docs/29-admin-table-and-form-style-guide.md`, and update it in the same pull request when a rule changes.

Do not treat generated Word or PDF files as the source of truth.

## Mandatory task-to-merge PR completion contract (all agents and delegated workers)

These standing owner instructions apply to **every implementation request** handled by GPT, Codex, Claude Code, subagents, or any successor agent, even when an individual prompt does not repeat them. They are a completion contract, not optional guidance. Explicit owner instructions to hold, stop, or change scope take precedence; platform access, required checks, and production-promotion gates cannot be bypassed.

1. **One request, one open PR.** Put all related changes requested in a task, including later refinements, fixes, tests, and documentation, into the **same ordinary, non-draft pull request** targeting `staging` whenever technically possible. Before creating a new PR, inspect whether the task already has an open PR and continue on it. Never start another PR just because CI fails, reviewers comment, or the branch is outdated. If genuinely separate PRs are needed, ask the owner for approval **before** splitting the task. Never add commits to a merged or closed PR.
2. **Own the entire verification and repair cycle.** After opening or updating the PR, check the **current head revision** for CI results, required risk-classified workflows under `docs/26`, review submissions and **all review threads**, merge conflicts, and whether the branch is outdated against its target. Fix every failure and actionable comment on that same open PR; explicitly **Resolve** each addressed GitHub review thread so it displays as **closed/collapsed**, not merely answered. Bring the branch up to date when necessary, rerun the required checks on the new head, inspect newly arriving CI/review feedback, and repeat until all gates are clean. Do not declare completion because a push succeeded, a review was requested, an old commit passed, or a comment was answered without resolving its thread. If asynchronous checks are still pending when execution must end, state precisely what remains pending and arrange a supported continuation/handoff; never claim to be monitoring autonomously after the agent stops.
3. **Mandatory automatic merge into staging.** The owner gives **standing authorization and instruction** to merge a task's PR to `staging` **immediately**, without requesting further approval, once the final current head has every required check green, all actionable comments fixed, **zero unresolved review threads (all closed/collapsed)**, no merge conflicts or required branch update outstanding, all required approvals satisfied, and **no active `hold-merge` or other explicit owner hold**. Recheck merge eligibility immediately before merging; do not merge on stale evidence. After merging, verify the merged state and report the PR URL and outcome. Never automatically merge to `main` or promote to production; those require the separate runbook gates and explicit owner authorization.
4. **No silent abandonment.** Continue the same PR through successive CI, review, and outdated-branch rounds as long as tools and access permit. Do not stop at the first error and hand the repair back to the owner. If blocked by permissions, infrastructure, unavoidable tool limits, or a decision only the owner can make, exhaust authorized alternatives, ask one specific question when needed, and record the exact PR, blockers, uncompleted checks, and next action. Preserve or close abandoned PRs and safely clean up task branches according to the branch-lifecycle policy; never pretend a blocked PR is green or merged.

## Efficient agent operation (applies to every agent working in this repo, including Claude Code, its subagents, and Codex)

Verification effort must scale with actual risk, not run at maximum thoroughness by default. This repo's own history shows the failure mode in both directions: skipping a check that later broke CI, and burning enormous time/token budget re-running full suites for changes that never needed them. Avoid the second failure mode as deliberately as the first:

1. Classify risk with `docs/26-ci-risk-classification-and-agent-merge-policy.md` before deciding how much to verify, and size the check to the classification. A change docs/26 classifies as low risk gets the fast check, not the full battery "to be safe."
2. Scope checks to what the diff actually touches. A small, single-concern fixup gets a typecheck plus the specific test file(s) covering that code — not a repeat of the full unit/integration/e2e/build suite already run for the commit it's stacked on, unless the fixup itself touches schema, auth, or another genuinely high-risk area.
3. Never re-verify code that already passed verification and hasn't changed since. When stacking another small commit on top of an already-verified one, verify the incremental diff, not the whole history again.
4. Do not spin up a fresh isolated environment (a clean clone or worktree, a full dependency reinstall, a full production build) for a small, low-risk change unless docs/26 actually calls for that level of check. Check directly against a working tree already known to be clean first.
5. Never run the same verification twice — in parallel or in sequence — to double-check work a prior pass already fully covered. One thorough pass beats two redundant ones.
6. When several fixes are already identified together (e.g., multiple review findings on one PR spotted at the same time), fix and verify them in one batch and one push, not one round-trip per finding.
7. When waiting on a slow external process (a review bot, CI), wait for its actual completion signal instead of polling in a tight loop, and never send a duplicate request (e.g. another "please review") while one is already in flight.
8. Report concisely. State what changed, what was checked, and the result — skip narrating routine mechanics (individual commits, individual pushes, intermediate tool calls) that carry no decision for the reader.
9. After pushing a fix for a PR review comment or bot finding, mark that GitHub review thread "Resolved" yourself (the GitHub API/UI action that collapses the thread) in the same round — this is a separate, required step from fixing the underlying code, not implied by it. Do not leave an addressed thread open/uncollapsed for a human to close, and do not wait to be asked. A thread stays open only when it is genuinely still unaddressed.
10. **Never commit or push new work to a pull-request branch after that pull request has been merged or closed.** Before every patch/push, verify the pull request is still open. If it is merged or closed, stop using that branch for the task, branch from the current `staging` head (or `main` only for an explicitly declared production emergency under docs/09), apply the new changes there, and open a new pull request.

## Branch lifecycle and abandoned-work cleanup (all agents)

This policy applies to GPT, Codex, Claude Code, and subagents. Follow the detailed agent-specific rules in `docs/09-codex-working-rules.md` and `docs/10-gpt-collaboration-rules.md`.

1. Every implementation task must have an accountable branch and pull request. Start ordinary work from the latest available `staging`, using one new task branch; do not reuse a merged or closed PR branch, and never directly commit ordinary work to `main` or `staging`. Preserve the documented production-emergency exception.
2. **Never create a draft pull request, on any platform.** Open a normal, non-draft PR targeting `staging` in the same step as the first push of a task — never push a task branch and leave it without a PR. Continue subsequent changes, CI repairs, and review fixes on the same open PR; do not introduce a draft-to-ready step. A normal open PR is proposed code, not merged code. If PR creation is blocked, do not leave the branch published: disclose the exact branch, commit SHA, blocker, and recovery plan, and delete or hold the branch locally. Do not create an empty commit solely to open a PR.
3. A task is not finished merely because code was committed. Follow its PR through required CI, actionable review comments (including resolving addressed threads), and merge when authorized and eligible. Never push further work to a merged or closed PR branch.
4. When abandoning, superseding, or replacing an unfinished task, inventory its branch and PR before starting a replacement. Record whether any unique work must be preserved or transferred. Close an abandoned PR with a clear reason; delete the remote branch only after confirming no open PR uses it and no unshipped work would be lost. If deletion is unavailable, report the exact orphan and blocker for later cleanup.
5. Do not enable GitHub's repository-wide automatic deletion of merged PR head branches without explicit owner authorization and enforceable protections or rulesets excluding every intentionally retained branch. The owner currently keeps this setting enabled, with `main` and `staging` protected by rulesets; agents must never enable, disable, or otherwise change it, and must verify the actual repository setting before reporting its status. Before relying on a branch surviving the merge of its PR, confirm it has a protection or ruleset exclusion; otherwise it will be deleted on merge. Deleting a branch reference does not immediately remove its commits from Git history.
6. Automated housekeeping may delete only demonstrably safe, no-longer-needed branches after checking fresh refs, open PRs, protected/reserved branches, and retained unique work. Never auto-delete `main`, `staging`, a branch used by an open PR, an explicitly preserved branch, or a branch with uncertain/unshipped changes. Age or lack of a PR alone never proves safety. Closed-unmerged PR branches and untracked orphan branches require explicit safe-disposition evidence or human approval before deletion.
7. Before any bulk deletion, create a durable restoration manifest containing branch name, full tip SHA, decision reason, PR status, and deletion outcome; produce a dry-run report and recheck eligibility immediately before each deletion. Use least-privilege credentials and obey GitHub rules. Stop on authentication/policy denials; do not retry through alternate credentials or bypass controls without fresh user authorization.
8. Keep branch cleanup independent of unrelated code-change PRs. The task report must account for created, merged, abandoned, preserved, and undeletable branches so unfinished work never disappears silently.
9. **Self-cleanup at task completion (standing owner approval).** An agent finishing, abandoning, or superseding a task must delete every remote branch that task created and that is not the head of an open PR or a merged/preserved PR: stray task branches, earlier attempts, and abandoned follow-ups. This is the only standing deletion approval and covers only branches the agent itself created during the task. Several agents (Claude, GPT, Codex, subagents) may run concurrently, so a branch is the agent's to delete only if that agent created it in this task and its remote tip is still the exact commit that agent last pushed; if anyone else has pushed to it, or any open PR (from any agent, person, or platform) uses it as head or base, leave it untouched. Delete only with an atomic compare-and-delete: `git push origin --force-with-lease=refs/heads/<branch>:<recorded-full-tip-sha> --delete <branch>`. The server removes the branch only if it still points at that exact commit, so if anyone pushes even one commit in the gap, the deletion is refused and nothing is lost; a refusal means leave the branch alone and report it. Never delete with a plain `git push --delete`, the GitHub API, the GitHub UI, or any tool that cannot check the expected commit, and never with a wildcard or a list built earlier. Check the live PR list immediately before each deletion, and record the branch name and full tip SHA in the task report so it can be restored. If a branch holds work that was never merged and the owner has not said to discard it, ask instead of deleting. Never delete branches created by other agents or people, and never delete by pattern or age. If deletion is denied or unavailable, stop, report the exact branches, and do not try other credentials. Branches whose PRs merge are removed by GitHub's delete-head-branch-on-merge setting as described in item 5; agents do not change that setting.

## Merging pull requests (all agents, all platforms)

Applies to Claude Code, Codex, GPT, subagents, and any other agent or platform.

1. **Standing merge authorization (staging-targeted PRs only).** An agent may merge a pull request that targets `staging` without asking when all of these hold on its current head: the fast check and every full workflow required by `docs/26` have passed, the PR is mergeable and current with its base, no review thread is unresolved, and no hold (item 2) is recorded. This authorization never covers a PR targeting `main`: a promotion to `main` also requires every gate in the "Branch, environment, and deployment workflow" section of `docs/07-administrator-and-operations-runbook.md` (staging proof, UAT, migration rehearsal where applicable, and operator approval) and explicit owner approval.
2. **Hold for pending work, recorded in the PR itself.** When the owner tells any agent that more commits are coming to a PR, or that follow-up work on it is still in progress, that agent must record the hold in durable shared PR state before ending its turn: add the label `hold-merge` with a PR comment saying what is pending; **never convert a PR to draft**. Every merging agent must check the PR's labels and comments for a hold and must not merge while one is present. Conversation memory or handoff notes alone are not a hold. The agent that finishes the pending work pushes the commits, waits for CI and review to pass on the final head, then clears the hold (removes the label and says so in a comment). This keeps the number of PRs and deployments down.
3. Pushing further commits resets the checks: re-verify the new head before merging, and never merge on the results of an earlier head.

## Cross-agent PR coordination and anti-proliferation (mandatory)

This section applies to GPT, Codex, Claude Code, delegated workers, and concurrent sessions. It adds coordination requirements to the existing task-to-merge contract; it does not weaken risk-based testing, review, branch protection, owner holds, or the distinct production-promotion gates.

1. **Inventory before creating or repairing.** Inspect every currently open PR against the repository and identify its owner/task, head/base, changed files, dependencies, pending CI, review threads, merge holds, and overlap with the requested work. Search for the same task, not merely an identical PR title. If a relevant PR exists, continue that PR and branch. A new repair/follow-up PR for an unmerged PR is forbidden unless the owner explicitly approves a technically necessary split after hearing why it cannot be done on the original branch.
2. **One shared coordination record.** Use GitHub PR descriptions, comments and labels as durable coordination state, not private chat context. Record blocking dependencies and active ownership in the affected PR; when work is still pending, use the existing `hold-merge` label plus an explanatory comment. Identify the responsible PR number and specific remaining action. Before touching a branch, recheck its latest head and any other agent's newer commits; do not overwrite concurrent work.
3. **Repair in place and batch findings.** Fix failing CI, review comments, conflicts, outdated branches, documentation and required tests on the same open PR. Consolidate known fixes into the fewest necessary pushes. Resolve/collapse each addressed review thread with GitHub's thread-resolution action, not merely a reply. Never create a second PR simply to repair findings on the first one; historical exceptions do not create precedent. If a fix truly cannot be placed on the existing branch, seek explicit owner authorization before opening a dependent PR.
4. **Coordinate merge order.** Review dependencies and changed-file overlap across open PRs. Complete independently mergeable staging PRs without unnecessary waits; for dependent changes, merge prerequisites first, update remaining branches against their current base, and rerun all checks required on the resulting head. Never merge a PR while another active PR or owner has recorded a legitimate hold on it. Do not let an in-progress staging PR slip into a production-promotion PR unnoticed: refresh and reverify the complete staging snapshot before any promotion.
5. **Finish, don't multiply.** After each change, follow the current-head checks, new reviews, thread resolution, mergeability and branch currency to a real outcome. Automatically merge clean authorized staging PRs; never auto-merge to main. If work cannot finish in the current execution, write a concrete PR-specific handoff/blocker in GitHub and report it to the owner; do not claim background monitoring. Close truly abandoned or superseded PRs with a reason and safely clean up only branches permitted by the existing branch-lifecycle rules, preserving unique work.
6. **Report one repository-wide status.** When coordinating multiple PRs, report each open PR's URL, target, checks, unresolved threads, base currency, holds, blockers, dependencies and next action; distinguish queued/running from failed and successful. State the intended merge order and whether the repository is ready for staging or production promotion. Do not open another PR to record this inventory.
